# EPCLM-002-A0 — A0-v0.2 Screening Protocol

Status: implementation-ready development screening plan. This plan does not amend or replace the frozen A0-v0.1-full protocol at research/governance/validations/epclm-002-a0-persistent-state-recall/protocol.json.

## Purpose

The screening run answers four mechanism questions: whether persistent state retains useful history; whether a reader can answer after raw context removal; how recall changes with fact load and distractors; and whether Cellular State shows a measurable difference from Flat Recurrent State.

The run is a mechanism screen, not a final model benchmark. Write/update/retention, routing, autoregressive language modeling, and efficiency remain outside A0 and belong to the later 002-B, 002-C, NCA-LM, and 002-E workstreams.

## Frozen screening matrix

| Variable | Values |
| --- | --- |
| Facts per episode | 1, 8, 32 |
| Distractors per episode | 0, 64 |
| State architecture | Flat Recurrent, Cellular |
| Overwrites | 0 (fixed) |
| Query distance | Fixed by the existing task generator |
| State budget | Existing matched ModelConfig budget |
| Evaluation rules and metrics | Frozen EPCLM-002-A0 v1 implementation |

There are six task conditions and two learned architectures, for 12 architecture-condition cells. The target is 128 episodes per cell (1,536 screening episodes). The same deterministic evaluation seed, episode IDs, query keys, and targets are used for both architectures within each condition. A separate 32-episode-per-architecture pilot at 32 facts and 64 distractors measures the highest-load runtime; those 64 pilot episodes are engineering measurements and are not counted toward the 1,536 screening episodes.

The pilot and screening use separate evaluation seeds. No screening sample is reused as pilot evidence. The pilot trains each architecture with the existing 500-step, batch-size-8 trainer on the Kaggle GPU. The frozen reader/evaluator remains on its existing CPU path; the pilot records that device and its end-to-end per-episode wall time.

The launcher computes a feasible per-cell episode target from observed timings, capped at 128. It uses the larger architecture-specific P95 episode time from the high-load pilot and a conservative per-cell overhead estimate. If the estimate is below 128, the run records the capacity-adjusted target and cannot be described as a 128-episode-per-cell screen. If the run times out before its selected target completes, every unfinished cell remains INCOMPLETE; partial outputs are resumable under the same identity.

## Runtime budget

| Budget | Seconds |
| --- | ---: |
| Notebook hard limit | 7,200 |
| Screening execution budget, including training, pilot, evaluation, and checkpoint writes | 5,400 |
| Result publication reserve | 600 |
| Safety margin for notebook setup and long-tail runtime | 1,200 |

A measured P95 is a planning estimate, not a guarantee. The launcher retains the fixed execution deadline, saves resumable progress, and publishes incomplete status if a cell cannot finish.

For the capacity report, let T_exec = 5,400, T_preflight be preflight and setup time, T_train be observed training time excluding checkpoint writes, T_checkpoint be measured checkpoint write time, T_pilot_eval be the measured pilot-evaluation time, T_cell_overhead be the conservative per-cell control/startup overhead, and T_episode_P95 be the largest observed episode P95 across the two architectures:

N_max_per_cell = floor((T_exec - T_preflight - T_train - T_checkpoint - T_pilot_eval - 12*T_cell_overhead) / (12*T_episode_P95))

The selected target is min(128, max(0, N_max_per_cell)). The report records every term, the two architecture-specific P50/P95 values, checkpoint saves, resume-load time, and publication time. The publication measurement is retained in Kaggle Output after the return step; published experiment metrics are committed before the publication duration is known.

## Predeclared diagnostic and stopping rules

These rules guide engineering diagnosis. They do not change formal hypotheses, thresholds, metrics, or the frozen protocol.

| Observation | Action |
| --- | --- |
| Full Context Oracle accuracy below the frozen 0.99 minimum | Stop interpretation; inspect task generation and evaluation integrity. The Oracle is an evaluator-only upper bound, so a failure indicates a task or measurement defect. |
| No Memory accuracy above 0.05 | Stop interpretation; audit leakage and task difficulty. |
| Both architectures below 0.95 on the 8-fact, 0-distractor condition | Do not expand samples; inspect state writing, persistence, and reading. The 0.95 reference is the frozen low-load learned-cell threshold and is used here only as a diagnostic. |
| Both architectures at or above 0.99 in every screening condition | The screen has insufficient separation. Do not adaptively add load in this run; propose a separately reviewed follow-up. |
| Cellular accuracy trails Flat by more than 0.05 at 32 facts and 64 distractors | Inspect state capacity and update behavior before confirmation. |
| Absolute Flat–Cellular difference is below 0.05 in every condition | Report no screening-level evidence of a practical Cellular advantage. Do not claim an advantage. |

At binary accuracy 0.5, the usual independent-binomial 95% margin is approximately ±8.7 percentage points for 128 independent episodes and ±4.9 points for 400; these are rough planning values, not the confirmatory analysis. Episodes are the sampling unit because multiple query outcomes within one episode may be correlated. A0-v0.2 has one training seed and 128 target episodes per cell at most; it cannot establish small differences. Confirmatory work selects two or three conditions after the screen, targets about 400 total independent episodes per condition across at least three training seeds, uses the same evaluation samples for paired architecture comparisons, and reports paired bootstrap or McNemar-style uncertainty at the episode level and between-seed variance. Confirmatory design and exact sample size must be preregistered separately and may be adjusted from the observed screening effect and variance.

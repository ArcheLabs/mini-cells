CLM 架构基准实验实施方案
版本：v1.0｜用途：后续正式实现与实验执行的协议基线
0. 执行摘要
本阶段直接比较三种架构：CLM、标准 MoE、Dense 全激活参考模型。不再要求 C-sync 找到与 A 组精确匹配的随机 Connection 路径，也不把 C-sync 匹配成功作为架构基准的前置条件。

这只意味着研究问题转为“CLM 作为完整架构，能否在模型质量与资源成本之间提供实际优势”。它不意味着此前已证明 CLM 的 Connection 学习优于随机路由，也不意味着 C-sync 的 NO-GO 已解决。

采用分阶段执行，避免在基线、数据或初始化不公平时消耗正式训练预算：
1. 阶段 0：仓库与实验资产审计，不启动科学训练。
2. 阶段 1：冻结配置并完成实现验证，只做必要测试与短程冒烟。
3. 阶段 2：小规模筛查，CLM / MoE / Dense，使用 Development 数据，不宣称最终结论。
4. 阶段 3：独立确认，仅在筛查达到预定义推进条件后执行。
5. 阶段 4：规模化语言建模或持续学习，作为后续决策。
完成文档或实现代码不自动授权正式 GPU 训练。正式训练必须在配置、数据、初始化和统计判据冻结后，经明确 GO 决策启动。
1. 研究目标
1.1 核心目标
评估 CLM 是否能以较低的 Connection / 路由参数开销，在可比的计算预算下达到与标准 MoE 相近的模型质量，并呈现有意义的资源效率优势。
1.2 主要研究问题
- RQ1 — 模型质量： 在共同任务、训练数据、Cell/Expert 参数预算和可比激活计算量下，CLM 的独立评测 NLL 与标准 MoE 相比如何？
- RQ2 — 路由开销： CLM 的 Connection 参数量是否低于 MoE Router？总参数量、激活 FLOPs、推理延迟和峰值内存是否因此改善？
- RQ3 — Dense 参考： CLM 与 MoE 相对于全激活 Dense 参考模型，呈现怎样的质量—计算成本权衡？
- RQ4 — 可复现性： 结果是否在多个配对 Seed 上保持方向一致，而非由单个初始化或数据顺序造成？
1.3 本阶段不回答的问题
- 不单独证明 Connection 学习优于随机 Connection。
- 不证明 Cell 专门化必然有利或会持续扩大。
- 不证明 CLM 在所有任务或大规模 LLM 上优于 MoE。
- 不把持续学习效果混入第一轮架构比较。
- 不把 Dense 称为理论性能上界；它只是一个明确配置的全激活基准。
2. 既有结果如何处理
1. 保留此前 CLM003 A/B/C 筛查、C-sync 工程实现及历史结果，不覆盖、不改写。
2. C-sync 精确幅度匹配不再是架构基准的前置条件；其 NO-GO 仍是该组件当前状态，不应标记为已通过。
3. 旧筛查使用过的 Confirmation 数据不得再次冒充独立确认集。
4. 旧 CLM003 父 Checkpoint 中的 Cells 已与 Connection 协同适应，不应直接作为 CLM、MoE、Dense 的中性共同初始化，用于声称从头训练的架构优劣。
5. 既有 CPU Phase 0 门禁无需重复运行，除非本阶段代码改动影响相应测试。
3. 实验组与基准定义
组别	定义	主要用途
A — CLM	使用当前 CLM Connection 机制决定 Cell 执行/调用路径，按既有训练算法更新 Connection 与 Cells	候选架构
B — Standard MoE	使用标准可学习 Router（例如 softmax gating + top-k expert selection），采用项目选定的常规负载均衡/容量处理	主要架构基准
C — Dense reference	使用相同 Cell/Expert 模块库，每次前向激活全部模块；采用预先固定、无学习的聚合/组合方式	全激活质量与成本参考


3.1 共享组件原则
- 尽可能使用相同 Cell/Expert 模块实现、单模块宽度与深度、输入输出接口、归一化和残差约定。
- 三组 Cell/Expert 初始权重应来自同一份未针对 CLM Connection 进行适应的初始化，并按 Seed 配对。
- 使用相同 tokenizer、上下文长度、训练语料版本、数据顺序、训练 Token 预算和评估实现。
- 架构差异必须来自协议明确列出的组件；不得为某组额外加入未注册的预训练、损失或数据处理。
- Dense 的聚合方式必须在训练前固定；不得根据确认集结果挑选 sum、mean 或其他组合方式。
3.2 Dense 的解释边界
Dense 激活全部 Cell/Expert，通常会有更高的每 Token 计算量，因此不是自动计算匹配的基线。报告必须同时列出质量与实际成本，不能只比较 NLL，也不能把 Dense 结果解释为纯粹的路由差异。
3.3 MoE 配置
优先复用仓库中已有、可复现的标准 MoE 实现，不为本实验发明新 Router。至少固定并记录 Router 形式、top-k、专家数量与容量规则、负载均衡辅助损失及系数、优化器/学习率/调度、token dropping 或 capacity factor、路由噪声、初始化与随机 Seed。

若仓库没有可用的标准 MoE 实现，阶段 0 只报告缺口和最小实现方案，不得悄悄使用未经审查的简化 Router 并称其为标准 MoE。
4. 公平比较规则
不同架构不可能在所有维度完全相同。本实验优先保证共同任务、Cell/Expert 参数库、训练数据和 Token 预算可比，并透明报告实际计算差异。
4.1 主要比较模式：共同 Cell/Expert 预算
- 三组使用相同数量、同结构的 Cell/Expert 模块及其初始权重。
- CLM 与 MoE 的路由机制按各自定义运行；记录每 Token 实际激活模块数、实测/验证 FLOPs 和路由参数量。
- 在不改变核心架构语义的前提下，尽量让 CLM 与 MoE 的平均激活 FLOPs 接近。工程目标建议为相差不超过 10%；若无法达到，不得声称“计算匹配”，必须报告实际差异并按给定预算下的架构比较解释。
- 不强行匹配 Router/Connection 参数量，因为路由开销差异本身就是研究对象。
- 训练 Token 预算必须一致。若步数、批次大小或序列长度因实现限制不同，必须在开始前说明并记录，不能只用相同步数声称预算相同。
4.2 Dense 比较模式
Dense 使用同一 Cell/Expert 参数库并激活全部模块，报告 NLL、总/可训练参数量、每 Token FLOPs、吞吐、延迟和峰值内存。第一轮不要求额外实现计算匹配的缩小 Dense 模型；除非已有实现可低成本复用，否则留作后续扩展。
4.3 初始化偏差门禁（硬门禁）
- 优先从未与 CLM Connection 协同适应的共同 Cell 初始化开始。
- 若存在可复现的早期父 Checkpoint，核实其训练历史、Cell 权重哈希和来源。
- 若只能获得已与 CLM Connection 协同适应的 Checkpoint，它不能作为中性主实验起点。可另做“继承状态上的继续训练”探索实验，但必须标记为 continuation comparison，不得与从头架构比较混为一谈。
- 若共同初始化无法恢复，阶段 0 结论为 NO-GO，先解决初始化来源，不启动正式训练。
5. 数据与任务设计
5.1 分两层解释结果
层 1：受控任务筛查。 可复用现有 Story/Arithmetic 合成任务，快速检查三种架构是否能训练、路由是否工作、结果是否明显崩坏。但必须建立新的、未用于旧 CLM003 确认的生成 Seed / 模板划分。此层只支持受控合成分布上的结论，不能称为 LLM 竞争力证明。

层 2：小规模自然语言建模确认。 若项目已有许可明确、可复现且版本可固定的自然语言语料，确认许可和处理流程后使用它作为进入规模化阶段的必要证据。若没有合适语料，阶段 0 必须提出数据候选、许可证、版本和拆分方案供批准，不得自行用不透明数据集替代后直接训练。
5.2 数据隔离
建立并记录 Train、Development、Confirmation。Calibration 只有在确实需要独立校准时才保留；否则在 manifest 中标记 not_used，不要为形式增加无用途的数据拆分。

每个 split 记录来源、生成规则/版本、样本数或 Token 数及 SHA-256。Confirmation 不得用于模型选择、阈值调整、路由规则选择、提前停止规则调整或调参。如果旧确认集已被反复查看，不能再次称为独立 Confirmation。
6. 指标
6.1 主要质量指标
- 主要指标： 独立评测集平均 Token Negative Log-Likelihood（NLL，nats/token）。
- 可报告 perplexity，但 NLL 是统计比较主指标。
- 任务准确率/成功率可作次要指标；不得看到结果后再把表现更好的指标改为主指标。
6.2 主要效率指标
- 总参数量、可训练参数量；
- Connection/Router 参数量及其占总参数比例；
- 平均每 Token 激活 Cell/Expert 数；
- 每 Token 实测或经验证的 FLOPs；
- 训练吞吐（tokens/s）与训练总成本；
- 推理延迟 p50/p95、吞吐；
- 峰值设备内存；
- 能耗仅在设备和工具可靠支持时报告，否则标记未测量。
6.3 路由诊断指标
- CLM：路径长度分布、Cell 使用频率、路由熵/路径多样性、Connection 参数量；
- MoE：专家负载分布、token 分配比例、负载均衡损失、路由熵；
- Dense：全部模块的激活情况与实际成本。
诊断指标不能替代最终模型质量，也不要求 Cell 分化在训练中持续扩大。
6.4 持续学习指标（后续阶段）
后续另行注册顺序任务实验，衡量新任务学习效果、旧任务保持、遗忘、适应速度和资源成本。本轮不把持续学习结果与架构基准混合。
7. Seed、预算与统计规则
7.1 分阶段 Seed
- 工程冒烟：1 个短程配置，仅检查程序能运行。
- 筛查：建议至少 3 个配对 Seed，固定训练 Token 预算；使用 Development 数据，不打开独立 Confirmation。
- 确认：仅在筛查达到推进条件后执行。确认 Seed 数须在打开 Confirmation 前，根据筛查阶段 Seed 间变异、最小有意义差异和预算确定并冻结；不得根据 Confirmation 结果追加/删减 Seed 以获得想要的结论。
若资源只允许少量 Seed，应将结论定位为探索性并报告不确定性；方向一致不自动等于统计确认。
7.2 配对设计
同一 Seed 下，三组尽可能共享 Cell/Expert 初始权重、数据顺序和 Token 顺序。架构专属随机流（如 Router 初始化、随机路由）必须单独记录且可复现。
7.3 主要效应量
定义 Δ_CLM-MoE = NLL_CLM − NLL_MoE：
- Δ < 0：CLM NLL 更低；
- Δ > 0：MoE NLL 更低。
预先定义可接受的非劣界限 delta_nll_noninferiority（nats/token）和最小实际效率收益阈值。界限必须在 Confirmation 解封前确定并写入 manifest，根据项目可接受的质量损失确定，不得从 Confirmation 结果反推。

若团队无法合理确定非劣界限，则报告效应量和区间，不得宣称“CLM 与 MoE 等效/非劣”。
7.4 统计报告
- 报告每个配对 Seed 的差值、均值、区间估计和所有失败运行。
- 同时报告每样本/序列的 NLL 分布；可用按样本重采样的 Bootstrap 估计评估集不确定性。
- 不得把同一模型中的每个 Token 当作完全独立的 Seed 来夸大统计显著性。
- 主要比较预先设为 CLM vs MoE；Dense 为参考。其他比较属于次要分析，必要时进行多重比较校正。
8. 推进与停止规则
阶段 0 — 审计与冻结前检查（不训练）
必须确认 CLM/MoE/Dense 实现入口与配置位置、可复现共同初始化、数据来源/许可/划分/哈希、设备与成本记录能力、统一 NLL 评估器，以及参数量和 FLOPs 的测量方法。

交付审计报告。若共同初始化、可比模型接口或数据隔离存在关键缺口，NO-GO。
阶段 1 — 实现验证（不做完整训练）
完成配置、模型适配器、指标记录与测试。执行单元测试、一次短程端到端冒烟、参数量/激活模块数/FLOPs 一致性检查、数据 split 隔离检查和同 Seed 可复现性检查。不重复未受本次改动影响的 Phase 0 门禁。
阶段 2 — 小规模筛查
- 执行 CLM、MoE、Dense 配对筛查；
- 至少 3 个 Seed，固定 Token 预算；
- 只用 Development 数据作筛查；
- 保存完整日志与成本账本；
- 不在此阶段宣称确认性结论。
推进阶段 3 的条件须在训练前写入 manifest。建议条件：CLM 训练稳定；NLL 没有明显超出预先定义的可接受范围；并且至少在 Connection/Router 参数开销或实际推理成本上出现预期方向的收益。阈值必须具体化，不能事后主观判断。
阶段 3 — 独立确认
只有阶段 2 达到推进条件才执行：
- 冻结代码 SHA、配置/数据哈希、Seed 列表、预算和统计判据；
- 使用封存 Confirmation；
- 不根据中途 Confirmation 结果修改训练规则；
- 完整报告质量、参数、计算、延迟、内存和不确定性；
- 输出 GO/NO-GO。
阶段 4 — 规模化与持续学习（后续决策）
只有阶段 3 显示 CLM 在质量—资源权衡上有实际价值，才考虑扩大规模或进入持续学习实验。规模化基准和持续学习应分别注册，不在本阶段一次性实现全部实验。
9. 结果解释矩阵
观察结果	结论与行动
CLM 达到预注册 MoE 非劣标准，并有明确路由参数或推理成本优势	支持扩大 CLM 评估
CLM 质量更好且成本可比	强正向结果；独立复现后扩大
CLM 质量接近但成本无实际改善	实用价值尚不明确；检查 Connection 参数与执行成本
CLM 更省资源但质量明显更差	只能讨论特定低资源应用，不能宣称通用替代 MoE
CLM 质量更差且没有成本优势	停止规模化，先审查路由/Cell 训练机制
结果随 Seed 大幅变化或区间很宽	证据不足；检查初始化、稳定性和样本量
初始化或数据隔离有偏差	实验无效或仅为探索性；修复后重跑


10. 必须输出的实验产物
每次运行至少保存：
1. EXPERIMENT_MANIFEST.json：研究问题、组别、配置、阈值、Seed、预算和判定规则。
2. SOURCE_MANIFEST.json：Git commit、工作树状态、依赖版本和运行环境。
3. DATA_MANIFEST.json：数据来源、许可证、拆分、数量与哈希。
4. INITIALIZATION_MANIFEST.json：Cell/Expert 初始权重来源、训练历史、参数哈希及是否曾与特定 Router/Connection 协同适应。
5. 每组配置文件与完整训练日志。
6. METRICS.json：质量、参数量、FLOPs、吞吐、延迟、内存和路由诊断。
7. COST_LEDGER.json：墙钟时间、设备类型、实际 GPU/CPU 使用、Token 数、优化器更新数和失败运行。
8. RESULTS.md：逐 Seed 结果、效应量、区间估计、协议偏离、结论边界和 GO/NO-GO。
9. 结果发布的准确 Git commit SHA 与远端核验信息。
所有产物标记为 screening 或 confirmatory，不得覆盖此前 CLM003 发布记录。
11. 给 Codex 的实施任务
第一任务：只审计，不训练
1. 检查当前仓库中的 CLM、MoE、Dense/Cell 实现、配置入口、数据和 Checkpoint。
2. 找出可复现、未针对 CLM Connection 适应的共同初始化；若没有，明确报告。
3. 查明 Story/Arithmetic 数据能否独立重新划分；查明是否已有许可明确、可复现的自然语言语料。
4. 检查 NLL 评估、参数量、FLOPs、延迟、内存和成本账本是否可复用。
5. 输出 ARCHITECTURE_BENCHMARK_AUDIT.md，列出实际文件/函数、能力、缺口、最小实现计划和 GO/NO-GO。不得启动训练。
第二任务：实现最小可运行基准
审计通过并获得明确批准后：
1. 复用现有组件，避免无关重构。
2. 实现统一配置和评估接口。
3. 确保 CLM/MoE/Dense 使用可比的 Cell/Expert 初始化、数据顺序和 Token 预算。
4. 增加必要测试和成本记录。
5. 执行单元测试与一次短程冒烟；不得自动开始筛查训练。
第三任务：筛查与确认
只有实现验证通过、配置和判据冻结后，才由用户明确批准启动阶段 2。阶段 2 完成后，先报告结果并等待决定是否进入阶段 3。不得自动进入独立确认或规模化训练。
12. 最终决策原则
本阶段成功标准不是“CLM 必须在所有指标上超过 Dense 或 MoE”，而是回答：

在预先规定的质量容忍度下，CLM 是否能以更低的路由参数开销和/或更低的实际推理成本，提供有竞争力的模型质量？

若是，继续规模化与持续学习研究；若否，则依据质量—成本曲线决定优化路由算法、调整架构或停止当前路线。结论必须与实际数据规模、初始化来源、训练预算和统计不确定性一致。
